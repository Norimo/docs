## Finding 1: overlay addresses offered as peer endpoints

You were right about the mechanism, and it was worse than one hole. Three separate paths let a flannel address into the peer path, and each needed its own gate, because a peer running older code keeps advertising and probing the looping address:

1. **Advertising.** Local endpoint discovery skipped only loopback and the Peerlify adapter, so `flannel.1` and `cni0` were offered like any other interface.
2. **Accepting.** The daemon only refused candidates inside the overlay subnet itself, so a peer's `10.42.1.0` passed.
3. **Learning and keeping.** The UDP layer adopted any authenticated inbound source as a candidate and deliberately preserved the active endpoint when a new candidate list omitted it. So even after filtering, a peer probing through the loop got the path validated on our side and it could never be evicted.

What changed, in the order you suggested:

- A built-in exclusion list of overlay, bridge and tunnel interfaces: `flannel*`, `cni*`, `cali*`, `vxlan*`, `cilium*`, `kube-*`, `weave*`, `docker*`, `br-*`, `virbr*`, `veth*`, `lxc*`, `lxd*`, `wg*`, `tun*`, `tap*`, `utun*`. Matching is case-sensitive so a Hyper-V host's `vEthernet (External Switch)` uplink is not caught by `veth*`.
- Two new settings, `TapClient.Relay.ExcludedInterfaces` (name patterns) and `ExcludedAddressRanges` (CIDRs), for anything the built-in list misses. This is the "remove" counterpart to `LocalAnnouncedEndpoints` that you noted was missing.
- `peerlify telemetry` now prints an `Excluded local` line so you can see the policy at work.

Verified on two Ubuntu 24.04 VMs in different regions, inbound closed except SSH, k3s v1.36.4 with `--flannel-iface Peerlify`, both nodes Ready:

| | No k3s | k3s running, fixed build |
|---|---|---|
| Local endpoints | NIC and public address only | NIC and public address only; `Excluded local: 100.64.0.1, 10.42.0.0, 10.42.0.1` |
| Peer endpoint | public address, p2p | public address, p2p, never migrated |
| `ping -c 50 -i 0.2` | 0% loss, 19.6 ms | 0% loss, 18.2 ms |

| `iperf3 -P 4 -t 15`, pod to pod | | 124 / 118 Mbit/s |
| `peerlify-daemon` CPU | under 1% | under 1% |

## Finding 2: control-plane fallback without TLS validation

Fixed in 2.7.0. Both control-plane endpoints, the hostname and the bare-IP fallback, now use validated TLS, and a shipped daemon cannot be switched back to unvalidated.

- The hostname endpoint is validated against the system trust store, like any CA-issued certificate.
- The fallback endpoint serves one stable certificate on every replica, and that certificate's SHA-256 fingerprint is compiled into the daemon. Only that certificate is accepted there. Anything else, on either endpoint, is rejected and the fingerprint it presented is logged.
- `UnsafeSkipTlsValidation` no longer exists in release builds: it is compiled out, so no configuration file, including your preserved `/etc/peerlify/appsettings.json` that still says `true`, can turn validation off. The daemon logs that the setting is ignored and validates anyway. The shipped configuration carries no TLS settings at all.

Verified on the lab: with the old configuration still on disk, the 2.7.0 daemon validates the hostname endpoint and signs in normally. Pointed at an impostor control plane with a self-signed certificate, it refuses every connection and logs the fingerprint. Pointed at the fallback address alone, it accepts the pinned certificate, registers and brings the data plane up. The fallback port is open again, so that path is live for every 2.7.0 daemon.

## Finding 3: throughput and CPU under load

Fixed by fixing finding 1.

- `TapClient.Adapter.OutboundProcessingWorkers` is a dead setting: nothing reads it. The outbound path is a single serial pump by design (it was made non-blocking after an incident where sends to unreachable peers stalled it). We will delete in the next release. 

## Finding 4: installer fails without a terminal

Fixed exactly as you suggested: the installer now probes with `sudo -n true` first and only falls back to the interactive `sudo -v` when a terminal is attached, so `ssh vm 'curl ... | sh'` works on a NOPASSWD image. The fix is live at `pkgs.peerlify.net/install.sh`.

## Finding 5: address range overlap

The range is already per network: in the web console under Settings, General, "Subnet CIDR" (or `PUT /api/v1/network` with `subnetCidr`), any IPv4 range with a prefix between /8 and /30. Setting the network to something like `10.100.0.0/24` keeps it out of `100.64.0.0/10` entirely, so both overlays can coexist on a machine during a move. Changing it on an existing network reassigns device addresses, so do it before the migration starts rather than during. We take the point that the default lands inside that range and are reviewing it. Takes around 20-60 sec to propogate to all clients.  

## Finding 6: sign-in link lifetime

The link lifetime is a control-plane setting, now set to 15 minutes and live. `peerlify login` prints the expiry the server hands back, so any client version gets the longer window.

## Rerunning on your VMs

Update both VMs to 2.7.0. Since you installed from the apt repository:

```bash
sudo apt update && sudo apt install peerlify
```

or simply rerun the installer, which now works unattended:

```bash
curl -fsSL https://pkgs.peerlify.net/install.sh | sh
```

`peerlify status` reports `Version: 2.7.0.168` afterwards. Your configuration file is preserved. Things to expect on that build:

- `peerlify telemetry` shows an `Excluded local` line with `100.100.0.1` plus the flannel and cni addresses once k3s is up, and the peer endpoint stays on the public address.
- The journal shows `UnsafeSkipTlsValidation=true is ignored: this is a release build` because your preserved configuration still has the old key. That is the intended behaviour.
- The journal's `Control-plane TLS policy` line lists one pinned fingerprint: the production fallback certificate, built in.
